# IPQ60xx 软硬双加速：2026-11-11 上机实测

设备：太乙 `10.10.10.100`，ImmortalWRT SNAPSHOT `r0-5cd11f1`，
`qualcommax/ipq60xx`，kernel 6.18.55，aarch64 Cortex-A53 ×4，2 GB RAM。
经跳板机 `nas.tokisaki-kurumi.cc` 接入。

## 1. 这台机器的"PPE"是什么

必须先纠正一个会误导策略的事实：**这台 IPQ60xx 用的不是 NSS/ECM，而是
现代 `qca-ppe` 驱动**。

| 项目 | 实测值 |
|---|---|
| 驱动 | `qca_ppe`，**builtin**（`/proc/modules` 里看不到） |
| 设备树节点 | `3a000000.ppe`（QCA8075 PHY ×4） |
| debugfs | `/sys/kernel/debug/3a000000.ppe` |
| L3 能力 | **有**：`offload_entries` 含 `nexthop/nh_type/l3_if/ul_port`，流表 2048 条 |
| 拒绝原因词表 | 含 `snat_and_dnat`、`ipv6_nat`、`no_egress_l2_header`、`table_full` |
| 软件回退 | `cpu_xmit=Y` |
| NSS / ECM | **完全不存在**（`nss_modules=0`、`ecm_debugfs=0`） |

`scripts/ppe-probe.sh` 原来把 `qca-ppe` 归进 `nss_dev=1`，于是判定
`backend=nss-ecm`、建议 `ppe_mode=fallback`。**这个建议是错的**——这台机器
根本没有 NSS 可以 fallback。已修复，现在输出：

```
backend=qcom-ppe
qcom_ppe_module=1  qcom_ppe_debugfs=1  qcom_ppe_netdev=1
nss_modules=0  nss_netdev=0  ecm_debugfs=0
recommended=ppe_mode=dual
```

## 2. DPD 数据面在真机上跑通了

这是本轮的核心成果。构建与部署：

```

clang --target=aarch64-linux-gnu -static ... -o dpdctl                   # 913 KB
```

## 3. PPE 硬件加速为什么没动

`offloaded 0`、`live_entries 0`、`l3_interface` 只有表头。原因不是驱动不行，
而是**当前拓扑没有可卸载的对象**：

1. **所有端口都在 `br-lan` 里**（lan1/lan2/lan3），桥内流量由硬件交换机
   直接转发，**根本不经过 L3 / flowtable**，PPE 的 L3 卸载自然无事可做。
2. **WAN 无载波**（`wan rx=0 tx=0 carrier=0`），没有第二条路由段，
   无法构造 lan↔wan 的路由流。
3. `l3_interface` 表为空 = 没有任何子网被挂到 switch 端口上做 L3。

三个子板全部 `ingress_not_switch_port=0`、`egress_not_switch_port=0`、
`no_egress_l2_header=0`，说明**驱动没拒绝过任何东西**——它压根没被问过。

### 3.1 需要的硬件条件

要做软硬双加速的实测，必须凑齐：

- WAN 口插上网线并拿到载波（PPPoE 或 DHCP 都行）；
- 或者把 lan2 从 `br-lan` 拆出来给一个独立子网（**本轮没有做**：lan2 有
  13455 rx / 20393 tx 和真实设备，拆它会断别人网）。

一旦有第二段路由，`nft` 的 `flowtable ft`（已经带 `flags offload`）就会
把 lan↔wan 的流交给 `flow_block`，PPE 的 `offloaded/live_entries` 才会动。

## 4. 踩过的坑（都会误导后续判断）

1. **busybox `nc` 不支持 `-l -p`**。用它做 TCP/UDP 测试会"成功返回"
   但一个包都没发，导致误判"数据面没收到流量"。
   → 用 `iperf3`（镜像自带）。
2. **nftables 的 `accept` 只结束当前 chain**。在 priority `-20`/`-300` 的
   独立 chain 里 `accept` 不能绕过 fw4 `input`/`forward` 的 `policy drop`。
   必须 `nft insert rule inet fw4 input ...` 插进 fw4 自己的基链。
   这是前面十几轮"转发不通"的真正原因，与 DPD 无关。
3. **同一条 veth 的两端不能当两个网段**。第一次测试把
   `dpdtest0/dpdtest1` 做成同一个 veth 的两头，client 和 server 在同一
   二层域，路由器看不到任何转发。必须是两对独立 veth。
4. **`tc` 把 map pin 到 `/sys/fs/bpf/tc/globals/`**，而 `dpdctl` 只认
   `/sys/fs/bpf/dpd_*`。目前靠 map-id 扫描兜底，能工作，但这是真实的可
   移植性隐患（见第 5 节）。

## 5. 遗留问题

| # | 问题 | 影响 |
|---|---|---|
| 1 | `dpdctl` 的 pin 路径与 `tc` 不一致 | 靠 id 扫描兜底；多实例会认错 map |
| 2 | PPE 硬卸载未实测 | 缺 WAN 载波或独立端口，非代码问题 |
| 3 | ABI 21 的 apk 未进固件镜像 | `sdk` 已产出 `r9/r8`，固件构建还没跑 |

## 6. 复现命令

```sh
# 构建
clang -target bpf -O2 -g -DDPD_MODE_DEFAULT=1 \
    -I bpf/core/src -I /usr/include -I /usr/include/$(gcc -print-multiarch) \
    -c bpf/core/src/dpd_fastpath.bpf.c -o dpd_fastpath.bpf.o
clang --target=aarch64-linux-gnu -static -O2 -I bpf/core/src \
    -o dpdctl bpf/core/src/dpdctl.c

# 部署（设备上）
tc qdisc add dev <if> clsact
tc filter add dev <if> ingress bpf obj dpd_fastpath.bpf.o sec classifier/l2 da
dpdctl ifaces <in> <out>
dpdctl set mode stateful
dpdctl set enable 1
dpdctl status
dpdctl flows
```
